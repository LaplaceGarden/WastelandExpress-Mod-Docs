# 游戏内物品查询窗口设计文档

日期：2026-05-28

## 背景

《废土快递》的 Mod 开发者和玩家经常需要查询物品 ID、名称、描述、重量、价格、标签、装备字段等信息。当前仓库已经提供 `docs/database` 下的静态 CSV 数据，但它们主要面向外部文档查阅，不适合玩家在游戏内边玩边查。

本设计定义一个游戏内 Lua Mod：在游戏内打开一个只读窗口，以表格形式查看物品信息。

## 目标

第一版目标是提供一个游戏内「物品图鉴 / 物品查询器」窗口，支持：

- 在游戏内打开独立查询窗口。
- 查看物品、食物、装备、配件四类物品信息。
- 按名称、ID、描述、标签进行搜索。
- 按物品分类筛选。
- 在简约模式和详细模式之间切换。
- 保持只读，不修改游戏数据、存档或玩家库存。

## 非目标

第一版不做以下功能：

- 不发放、删除或修改物品。
- 不修改物品属性、价格、重量或标签。
- 不展示人员、派系、Buff、城市、任务、地牢技能等非物品数据。
- 不做菜谱、配方、自有城市合成等合成数据查询。
- 不做配方反查。
- 不做收藏、标记常用、历史记录。
- 不做 CSV 导出或联网更新。

## 数据范围

物品查询范围限定为四类数据：

- `物品.csv`
- `食物.csv`
- `装备.csv`
- `配件.csv`

这四类数据对应第一版 UI 中的四个分类：`物品`、`食物`、`装备`、`配件`。

数据来源采用运行时优先策略：

- 优先读取游戏当前运行时已经加载的物品数据，确保其他 Mod 新增物品也能被看到。
- 当前已文档化 API 不直接提供“枚举完整物品列表”的接口，因此运行时读取需要作为第一项技术验证。
- 如果运行时枚举不可用或部分类型读取失败，再使用随 Mod 分发的静态官方数据作为兜底。

不同来源没有的字段显示为空或 `-`。

## 数据模型

统一物品记录：

```text
ItemRecord
- id: number|string
- name: string
- sourceType: "物品" | "食物" | "装备" | "配件"
- sourceOrigin: "runtime" | "static"
- level: number|string
- weight: number|string
- price: number|string
- iconId: number|string
- description: string
- tag: string
- characteristic: string
- buffId: string
- func: string
- funcPlus: string
- needSource: string
- attackRange: string
- rawFields: table
```

`rawFields` 保留原始字段，用于详细模式兜底展示，避免字段映射不完整导致信息丢失。

## 窗口入口

第一版推荐通过 Lua 函数或控制台命令打开窗口，例如：

```lua
ItemBrowser_Open()
```

选择这个入口的原因：

- 当前文档明确支持 Lua 脚本触发和 `OnGUI` 绘制。
- 对游戏原生 UI 注入依赖更少，第一版风险更低。
- 后续可以再扩展为主界面按钮、快捷键或已有菜单入口。

## 界面结构

窗口顶部固定显示：

- 标题：`物品图鉴`
- 搜索框：搜索名称、ID、描述、标签
- 分类筛选：`全部`、`物品`、`食物`、`装备`、`配件`
- 模式切换：`简约`、`详细`
- 关闭按钮

窗口默认打开简约模式。切换模式时保留当前搜索词、分类筛选和选中物品。

## 简约模式

简约模式用于边玩边查，是默认模式。

布局：

- 左侧是物品列表表格。
- 右侧是当前选中物品详情。

左侧表格列：

- `ID`
- `名称`
- `分类`

右侧详情字段：

- 名称
- ID
- 分类
- 等级
- 重量
- 价格
- 描述
- 标签
- 特性
- 类型专属字段摘要

类型专属字段摘要示例：

- 装备：`BuffID`、`Func`、`FuncPlus`、`AttackRange`
- 配件：`BuffID`、`Func`、`NeedSource`
- 食物：`Characteristic`、`Tag`
- 物品：`Characteristic`、`Tag`

## 详细模式

详细模式用于完整查表和字段对比。

布局：

- 窗口主体切换为宽表格。
- 搜索和分类筛选仍位于顶部。
- 表格支持纵向滚动；如果实现条件允许，支持横向滚动。

建议列：

- `ID`
- `名称`
- `内部名 / 英文名`
- `分类`
- `等级`
- `重量`
- `价格`
- `图标ID`
- `描述`
- `标签`
- `特性`
- `BuffID`
- `Func`
- `FuncPlus`
- `NeedSource`
- `AttackRange`

第一版默认按 ID 升序排序。点击表头排序作为后续增强，不纳入第一版必需功能。

## 搜索与筛选

搜索输入匹配以下字段：

- ID
- 名称
- 描述
- 标签
- 特性
- 内部名 / 英文名

匹配规则：

- 输入纯数字时，优先按 ID 精确匹配，同时保留模糊匹配能力。
- 输入中文或英文文本时，对上述字段做不区分大小写的包含匹配。
- 分类筛选与搜索条件同时生效。

性能策略：

- 如果即时搜索在游戏内 GUI 中性能稳定，则输入时实时过滤。
- 如果实时过滤有卡顿，则改为点击搜索按钮后过滤。

## 状态管理

窗口状态包含：

- 是否显示窗口。
- 当前模式：简约或详细。
- 当前搜索词。
- 当前分类筛选。
- 当前选中的物品 ID。
- 当前滚动位置。

切换模式时必须保留：

- 搜索词。
- 分类筛选。
- 选中物品。

关闭窗口时第一版可以不持久化状态。后续版本如果需要记住模式和搜索条件，再使用固有函数 `Save` / `Load` 保存 Mod 自己的数据。

## 数据来源策略

第一版必须采用运行时优先、静态数据兜底的策略。

这样设计的原因：

- 运行时数据更接近玩家当前实际游戏环境。
- 其他 Mod 新增的物品只有在运行时数据中才可能被完整看到。
- 静态 CSV 只能代表文档仓库中已有的官方参考数据，不能覆盖所有玩家安装的 Mod 内容。

### 公开 API 现状

当前文档化 API 不支持直接查询完整物品列表：

- `ItemManager.md` 为空，没有公开 `GetAllItems`、`GetItemList` 或类似接口。
- `TradeManager:GetCurrentTraderData(int ID)` 只能获取某个交易者当前商品列表。
- `DungeonCityManager:GetProperty()` 和 `GetPropertyFood()` 只能获取地牢个人财产列表。
- `SelfCityManager:GetItemsInSelfCity(cityID, ID)` 只能按指定 ID 获取自建城中的物品。
- `SelfCityManager:TryGetItemCount(...)` 只能查询指定城市中指定物品数量。
- `OnEat`、`OnDrink`、`OnCure` 等触发函数只能拿到当次使用的物品实例。

因此，“运行时优先”不能依赖现有公开模块 API 直接完成，需要通过 `CS` 命名空间探测游戏内部数据管理类或运行时数据表。

### 数据加载顺序

1. 尝试通过 `CS` 命名空间或可访问的游戏数据管理类枚举当前运行时物品、食物、装备、配件数据。
2. 将运行时记录转换为统一的 `ItemRecord`，并标记 `sourceOrigin = "runtime"`。
3. 如果某一类运行时数据无法获取，则加载对应静态数据作为兜底，并标记 `sourceOrigin = "static"`。
4. 合并结果并按 `sourceType + id` 去重。
5. 如果运行时记录和静态记录 ID 冲突，优先保留运行时记录。

### 运行时数据验证

实现前需要验证以下能力：

1. Lua 能否通过 `CS` 命名空间访问游戏已加载的数据表或数据管理类。
2. 能否分别获取物品、食物、装备、配件四类数据。
3. 其他 Mod 新增数据是否会进入同一套运行时数据结构。
4. 运行时记录是否包含名称、ID、描述、标签、重量、价格等 UI 必需字段。

如果只能读取部分类型，例如能读取基础物品但不能读取装备，则已读取类型使用运行时数据，未读取类型使用静态数据。

### 静态兜底数据

静态兜底数据来自仓库中的四张 CSV：

- `docs/database/物品.csv`
- `docs/database/食物.csv`
- `docs/database/装备.csv`
- `docs/database/配件.csv`

为了避免游戏内解析 CSV 的编码和转义问题，静态数据建议在构建或打包 Mod 前预处理成 Lua table，例如 `item_data_static.lua`，随 Mod 一起分发。

## 错误处理

应处理以下情况：

- 数据文件缺失：窗口显示“物品数据未加载”，不报错刷屏。
- 某条记录字段缺失：该字段显示 `-`。
- 搜索无结果：显示空状态“没有找到匹配物品”。
- 选中物品不存在：自动清除选中状态或选中第一条结果。
- 运行时枚举失败：回退到静态数据，并在控制台输出一次错误摘要。
- 静态数据解析失败：对应分类显示为空，并在控制台输出一次错误摘要。

## 视觉与交互原则

- 窗口应是工具型 UI，不做装饰性设计。
- 信息密度优先，但默认模式不能遮挡过多游戏画面。
- 表格字体使用可读的小字号，行高稳定。
- 按钮文案短：`全部`、`物品`、`食物`、`装备`、`配件`、`简约`、`详细`、`关闭`。
- 搜索框占主要宽度，方便快速输入。
- 详细模式可以更宽，但仍应允许一键回到简约模式。

## 验收标准

第一版完成后应满足：

- 可以在游戏内打开和关闭物品查询窗口。
- 默认进入简约模式。
- 可以切换到详细模式，并切回简约模式。
- 可以看到 `物品`、`食物`、`装备`、`配件` 四类数据。
- 优先展示当前游戏运行时加载的物品数据。
- 在运行时数据不可用时，可以回退展示静态官方物品数据。
- 如果其他 Mod 新增物品进入游戏运行时物品表，查询窗口能显示这些物品。
- 搜索名称、ID、标签时能过滤结果。
- 分类筛选能正确过滤结果。
- 简约模式选中行后能显示详情。
- 详细模式能展示完整字段表格。
- 功能只读，不修改玩家库存、存档或游戏数据。
- 数据缺失或无搜索结果时不会导致 Lua 报错刷屏。

## 技术风险

主要风险：

- 当前已文档化 API 不直接支持枚举完整物品列表。
- 游戏是否提供稳定方式枚举运行时物品库仍需验证。
- 其他 Mod 新增物品是否进入同一套运行时数据结构仍需验证。
- 运行时数据字段可能和静态 CSV 字段不完全一致，需要做字段归一化。
- 游戏内 Lua 读取外部文件的能力不确定。
- CSV 编码不统一，运行时解析可能遇到中文乱码。
- `OnGUI` 每帧绘制，如果搜索和表格渲染不做缓存，可能影响性能。
- 宽表格在 Unity IMGUI 中的滚动和列宽控制需要验证。

缓解措施：

- 把运行时数据枚举作为实现计划中的第一项技术验证。
- 运行时读取失败时回退静态数据，确保窗口仍可用。
- 静态 CSV 预处理成 Lua table，减少运行时解析。
- 搜索结果缓存，只在搜索词、分类或数据变化时重新计算。
- 详细模式只渲染可视范围或限制单页行数，避免每帧绘制全部记录。
- 出错日志只输出一次，避免 `OnGUI` 或 `Update` 中反复 `print`。

## 后续扩展

后续可以考虑：

- 表头点击排序。
- 配方和菜谱关联查询。
- 物品来源说明。
- 记住上次打开模式。
- 快捷键打开窗口。
- 从已有游戏 UI 添加按钮入口。
- 收藏常用物品。
